# Автоматичні листи клієнтам

Шаблони редагуються в **Адмінка → Листи клієнтам** (`/admin/order-emails`). Є українська й англійська версії, редагування теми, подяки, наступних кроків, підпису та банківських реквізитів, попередній перегляд без надсилання. Номер замовлення, товари, кількість, ціни, знижка, підсумок, оплата та доставка додаються автоматично з даних замовлення. Нові тексти застосовуються після збереження.

## Коли надходять листи

- LiqPay: після підтвердження оплати сервером платіжної системи.
- Банківський переказ: після оформлення — лист із реквізитами; після переведення замовлення у статус «Оплачено» — підтвердження оплати. Працює також масове оновлення статусу.
- Лист надсилається на email, зазначений клієнтом. Оформлення без email, як і раніше, дозволене; для такого замовлення лист не створюється.
- Для міжнародної доставки використовується англійський шаблон, для Нової пошти — український. Сума береться зі збереженого замовлення в гривні.

## Одноразове підключення на сервері

1. Застосувати міграції **перед запуском нового коду**: `npx prisma migrate deploy`, потім `npx prisma generate`. Не використовувати `db push` для робочої бази.
2. У Google-акаунті `gerdanstudio@gmail.com` увімкнути двоетапну перевірку й створити пароль застосунку. [Інструкція Google](https://support.google.com/accounts/answer/185833?hl=uk). Зберегти пароль тільки в секретних змінних середовища сервера, не в Git чи формі шаблону.
3. Додати змінні середовища:

   ```dotenv
   SMTP_PASSWORD=<пароль застосунку Gmail>
   CRON_SECRET=<випадковий секрет для планувальника>
   ```

   За замовчуванням використовуються `smtp.gmail.com`, порт `465`, TLS, відправник `GERDAN <gerdanstudio@gmail.com>` і адреса відповіді `gerdanstudio@gmail.com`. За потреби підтримуються `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `MAIL_FROM`, `MAIL_REPLY_TO`.

4. Для цього проєкту на Vercel Pro розклад уже задано у `vercel.json`: `/api/cron/order-emails` кожні 5 хвилин. У **Project → Settings → Environment Variables** додати `SMTP_PASSWORD` і `CRON_SECRET` для середовища **Production**. Локальний `.env` не переносить ці значення в налаштування Vercel. Опублікувати новий код разом із `vercel.json`; розклад активується після production-деплою. Vercel сам додає заголовок авторизації з `CRON_SECRET`. [Налаштування розкладу](https://vercel.com/docs/cron-jobs/quickstart), [захист cron](https://vercel.com/docs/cron-jobs/manage-cron-jobs).

   Для іншого хостингу планувальник має виконувати запит кожні 5 хвилин:

   ```http
   GET https://gerdan.online/api/cron/order-emails
   Authorization: Bearer <CRON_SECRET>
   ```

   Секрет передається заголовком, не в URL. Перша спроба надсилання відбувається одразу після підтвердження замовлення; cron обробляє відкладені та повторні спроби. На Vercel Hobby цей п’ятихвилинний розклад не підтримується.

5. В адмінці зберегти тексти й банківські реквізити для обох мов. До першого збереження реквізити також читаються з `BANK_TRANSFER_DETAILS_UK` / `BANK_TRANSFER_DETAILS_EN`, якщо вони вже налаштовані.
6. Перевірити контрольне замовлення зі своєю адресою та отримання листа. Наявність конфігурації SMTP ще не підтверджує автентифікацію Gmail або доставку до скриньки.

На production надсилання вмикається автоматично. `ORDER_EMAILS_ENABLED=false` явно вимикає створення й обробку листів. Локальна розробка та Vercel Preview не надсилають їх без `ORDER_EMAILS_ENABLED=true`. Не використовуйте спільну з production базу для тестових листів.

## Повторні спроби

Завдання на лист зберігається в `OrderEmailDelivery` у тій самій транзакції, що й оформлення або підтвердження оплати. Перша спроба виконується через Next.js `after`, після HTTP-відповіді, тому очікування SMTP не затримує оформлення.

Після помилки завдання лишається в черзі: інтервали 1, 2, 4… хвилини, максимум 6 годин; фактична спроба — на найближчому запуску планувальника. Один запуск обробляє до 5 листів паралельно. Поля `sentAt`, `skippedAt`, `attempts`, `lastError`, `nextAttemptAt` показують результат без зберігання пароля чи тексту листа в журналі.

Унікальна пара «замовлення + тип листа» та блокування завдання захищають від повторних callback і одночасних обробників. Блокування зникає через 5 хвилин після аварійного завершення процесу. Для скасованих замовлень і вже оплачених запитів на переказ застарілі листи пропускаються. Історичні замовлення автоматично не розсилаються.

SMTP не гарантує доставку рівно один раз: якщо сервер прийняв лист, а процес завершився до запису `sentAt`, повторна спроба може створити дублікат. Для всіх спроб зберігається один `Message-ID`.

Перевірки без надсилання: `npm run test:email`, `npm run test:orders`, `npm run test:payments`, `npm run preview:email`.
